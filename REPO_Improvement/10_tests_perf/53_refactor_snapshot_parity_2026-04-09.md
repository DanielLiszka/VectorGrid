# Refactor Snapshot Parity Plan

Last updated: 2026-04-09

## Purpose

Define the narrow snapshot-artifact workflow used to compare canonicalized non-options outputs across refactors.

## Scope Boundaries

In scope:

- the snapshot bin `src-tauri/src/bin/ta_refactor_snapshots.rs`
- canonicalized versus raw snapshot outputs under `_write_test/refactor_snapshots/`
- refactor-diff usage for validation/meta-oriented artifacts
- the difference between snapshot parity and general artifact parity

Out of scope:

- options-related snapshots
- full benchmark or release gating
- broad snapshot testing across the entire app
- UI screenshots or browser snapshots

## Current User-Facing Behavior

The repo already contains a focused snapshot bin that writes raw and canonicalized JSON artifacts for validation/meta-related surfaces into a `_write_test/refactor_snapshots/` tree. This is useful because it gives refactor work a cheap diffable artifact lane, but it is intentionally narrow and must stay that way to remain interpretable.

## Current Code Surface

- `src-tauri/src/bin/ta_refactor_snapshots.rs` owns snapshot generation and canonicalization behavior.
- `_write_test/refactor_snapshots/validation_meta/` is the current output area for these artifacts.
- `scripts/check_output_parity.mjs` and related parity docs are adjacent but not identical tools.
- the validation and meta artifact structures generated by the bin are rooted in current app-core and report contracts.

## Current Verification Surface

- `cargo run -p ta_desktop_demo_app --bin ta_refactor_snapshots`
- manual diff review of raw and canonicalized snapshot outputs
- targeted parity or report tests when a snapshot diff suggests a deeper contract change

## Strengths Already Present

- the snapshot tool is intentionally narrow and therefore interpretable
- canonicalized output makes diff review easier for structured JSON changes
- the bin produces both raw and canonical views, which helps reviewers see what changed and what was normalized
- it provides a useful refactor aid without forcing the whole repo into snapshot testing

## Weaknesses / Failure Modes

- snapshot coverage is intentionally partial and can be mistaken for full parity
- canonicalization can hide ordering differences that may still matter in some contexts
- the tool currently depends on manual reviewer judgment rather than a more formal pass/fail layer
- the `_write_test` output path makes it easy to forget snapshots are ephemeral review aids

## Regressions To Avoid

- treating refactor snapshots as exhaustive artifact coverage
- expanding snapshot scope broadly without maintaining review clarity
- relying only on canonicalized output and ignoring raw output when ordering or exact structure matters
- using snapshot diffs without following up on whether they represent intended or unintended contract change
- allowing this surface to stay behaviorally “working” while contributor readability, diagnostics, accessibility where relevant, static-analysis cleanliness, or regression coverage degrades in a public-facing repo

- [JSON Schema getting started](https://json-schema.org/learn/getting-started-step-by-step) is relevant because snapshot parity is fundamentally about structured contract review.
- [Cargo run command docs](https://doc.rust-lang.org/cargo/commands/cargo-run.html) are relevant because snapshot generation is a dedicated headless-bin workflow.
- [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259) is relevant because snapshot canonicalization and JSON diff review depend on stable JSON semantics.
- [Criterion.rs book](https://bheisler.github.io/criterion.rs/book/) is relevant as a contrast because snapshot parity is structural review, not performance authority.
- [Clippy](https://github.com/rust-lang/rust-clippy)
  - relevant because public-repo quality work should include explicit static-analysis expectations alongside behavioral tests and perf gates

## Proposed Improvement Approach

1. Keep refactor snapshots narrowly scoped to high-value structured artifacts.
2. Preserve both raw and canonicalized outputs so reviewers can decide what changed meaningfully.
3. Use snapshot diffs as a refactor aid, not as a standalone release gate.
4. Cross-link meaningful diffs into the deeper parity or report-test surfaces when needed.
5. Treat test/perf code quality as part of the implementation scope: prefer stable, reviewable gates, exact commands, environment provenance, and raw evidence capture over brittle harness sprawl.

Public-repo quality focus:
- keep touched-file ownership, adjacent-doc sync, and acceptance evidence explicit
- preserve contributor readability, diagnostics, and static-analysis health alongside user-visible behavior
- prefer additive hardening over broad cleanup-only refactors that widen blast radius
- update tests, fixtures, screenshots, workbooks, or artifacts in the same change when behavior shifts

## Verification Plan

- run the snapshot bin around refactors touching the covered artifact surfaces
- review both raw and canonicalized outputs when meaningful diffs appear
- follow up with deeper tests or parity checks when a diff looks suspicious
- confirm the output tree and file names remain stable enough for repeat use
- run the relevant repo quality gates for any touched surfaces, including `cargo check --workspace` or a justified narrower Rust target plus `npm --prefix web run lint` and `npm --prefix web run typecheck` where frontend or desktop code is touched
- capture the exact commands, environment, raw outputs, and refresh reason needed to prove this verification or perf surface still deserves trust in a public repo

## Rollout / Fallback / Compatibility Notes

- preserve the current narrow, useful snapshot workflow
- prefer clarity and diffability over bigger snapshot coverage
- if snapshot noise grows, narrow the scope rather than normalizing everything away
- keep changes additive, preserve existing functionality, and avoid broad cleanup-only refactors unless they provide objective user or maintainer value and include the necessary migration notes
