# FE Accessibility Smoke Plan

Last updated: 2026-04-09

## Purpose

Define the current accessibility smoke layer so the built non-options frontend keeps a repeatable automated scan for major detectable accessibility regressions.

## Scope Boundaries

In scope:

- `web/scripts/check-a11y-smoke.mjs`
- built-app accessibility scans in mocked-Tauri mode
- shell, settings, command-palette, and task-center scan points

Out of scope:

- full manual accessibility review
- component-level a11y assertions
- options-specific surfaces

## Current User-Facing Behavior

The repo already ships an accessibility smoke script that builds the frontend, serves the built app, installs mocked-Tauri behavior, dismisses the startup overlay, and runs axe scans against multiple shell states. This is already a concrete automation layer, not a plan-only placeholder.

## Current Code Surface

- `web/scripts/check-a11y-smoke.mjs`
- `web/package.json`
  - `a11y:smoke`
- `web/src/components/CommandPaletteOverlay.vue`
- `web/src/components/TaskCenterOverlay.vue`
- `web/src/components/SettingsWorkspacePanel.vue`
- `web/src/components/VueWorkspaceShell.vue`

## Current Verification Surface

- `npm --prefix web run a11y:smoke`
- targeted component tests for affected overlays and shell surfaces

## Strengths Already Present

- accessibility smoke already runs against built output rather than only in component tests
- the script already scans multiple shell states instead of one page only
- the repo already uses Playwright plus axe rather than ad hoc DOM checks

## Weaknesses / Failure Modes

- automated a11y smoke is not a full accessibility review
- the script focuses on a few major shell states and can miss narrower issues
- mocked-Tauri mode can hide native-runtime-specific issues

## Regressions To Avoid

- removing the automated scan because component tests still pass
- treating a clean axe result as proof of full accessibility quality
- silently shrinking the scanned surface area without documenting it
- allowing this surface to stay behaviorally “working” while contributor readability, diagnostics, accessibility where relevant, static-analysis cleanliness, or regression coverage degrades in a public-facing repo

## External Research Summary

- [Playwright accessibility testing](https://playwright.dev/docs/next/accessibility-testing)
  - relevant because the current script already uses Playwright with axe-based scanning
- [Playwright best practices](https://playwright.dev/docs/best-practices)
  - relevant because a11y smoke should target stable user-visible states
- [Deque axe for Playwright](https://github.com/dequelabs/axe-core-npm/tree/develop/packages/playwright)
  - relevant because the repo uses `@axe-core/playwright` as the scanning engine
- [Clippy](https://github.com/rust-lang/rust-clippy)
  - relevant because public-repo quality work should include explicit static-analysis expectations alongside behavioral tests and perf gates

## Proposed Improvement Approach

1. Keep automated accessibility smoke as a built-output gate.
2. Preserve its role as a high-signal but partial check.
3. Expand scan targets deliberately when major shell surfaces change.
4. Pair automated scans with narrower component assertions and manual review when needed.
5. Treat test/perf code quality as part of the implementation scope: prefer stable, reviewable gates, exact commands, environment provenance, and raw evidence capture over brittle harness sprawl.

Public-repo quality focus:
- keep touched-file ownership, adjacent-doc sync, and acceptance evidence explicit
- preserve contributor readability, diagnostics, and static-analysis health alongside user-visible behavior
- prefer additive hardening over broad cleanup-only refactors that widen blast radius
- update tests, fixtures, screenshots, workbooks, or artifacts in the same change when behavior shifts

## Verification Plan

- run `npm --prefix web run a11y:smoke`
- rerun relevant component tests for changed shell/overlay surfaces
- run the relevant repo quality gates for any touched surfaces, including `cargo check --workspace` or a justified narrower Rust target plus `npm --prefix web run lint` and `npm --prefix web run typecheck` where frontend or desktop code is touched
- capture the exact commands, environment, raw outputs, and refresh reason needed to prove this verification or perf surface still deserves trust in a public repo

## Rollout / Fallback / Compatibility Notes

- keep a11y smoke additive; do not replace narrower accessibility-aware component assertions
- if the startup overlay path changes again, update the harness in the same change
- keep changes additive, preserve existing functionality, and avoid broad cleanup-only refactors unless they provide objective user or maintainer value and include the necessary migration notes
