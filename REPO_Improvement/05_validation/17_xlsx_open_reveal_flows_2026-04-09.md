# XLSX Open Reveal Flows Plan

Last updated: 2026-04-09

## Purpose

Plan improvements to validation XLSX save/open/reveal behavior so export paths, auto-reveal preferences, artifact-backed export, Stage 3 fallback, and report-folder actions remain consistent and non-destructive.

## Scope Boundaries

In scope:

- `web/src/services/validationService.ts`
- `web/src/services/historyService.ts`
- `web/src/services/metaService.ts`
- `web/src/stores/commandActionStore.ts`
- `src-tauri/src/commands_reports_api.rs`
- `src-tauri/src/commands_reports_shared.rs`

Out of scope:

- workbook content itself
- artifact indexing already covered in artifact docs
- options-related report/export flows

## Current User-Facing Behavior

The validation workspace already supports:

- report XLSX export
- reports-folder open
- optional auto-reveal after save
- artifact-backed export when the current run/validation pair matches a saved artifact
- base64 download fallback when direct save fails
- Stage 3 meta-report fallback when a validation artifact is not present

History and Meta views also support `open_path` first and `reveal_path` fallback behavior for saved reports and saved artifact files.

## Strengths Already Present

- export is already command-driven rather than filesystem-written from the frontend
- artifact-backed export already avoids reconstructing report payloads when a persisted validated run exists
- save failure already falls back to a download path instead of losing the export entirely
- open and reveal actions already degrade gracefully across several services
- Stage 3 meta-report fallback is preserved intentionally when validation state is absent

## Weaknesses / Failure Modes

- open/reveal fallback logic is duplicated across validation, history, meta, settings, and command-action layers
- auto-reveal can lead to slightly different status semantics depending on which service initiated the action
- direct report export, saved-run report open, and latest-report quick actions do not all share one path-action helper
- Stage 3 fallback and validation export semantics live in the same function, which makes accidental regression easy
- folder-open and file-open actions share similar concepts but are not documented as a single contract

## Regressions To Avoid

- removing Stage 3 fallback behavior
- breaking artifact-backed export preference for persisted validated runs
- changing auto-reveal so it stops revealing after a successful save
- losing base64 download fallback when filesystem save fails
- making history/meta saved-report actions behave differently from validation export actions without a deliberate decision
- allowing this surface to stay behaviorally “working” while contributor readability, diagnostics, accessibility where relevant, static-analysis cleanliness, or regression coverage degrades in a public-facing repo

## Proposed Improvement Approach

1. Freeze one shared policy for file and folder actions:
   - save
   - open
   - reveal
   - save failure fallback
2. Centralize frontend path-action helpers so validation, history, meta, and quick actions do not drift.
3. Keep artifact-backed export, Stage 3 fallback, and base64 fallback as explicit branches with dedicated tests.
4. Make status-line copy intentionally consistent across entry points.
5. Preserve additive behavior only; do not remove any current save/open/reveal path.
6. Treat validation/report code quality as part of the implementation scope: keep workbook/report contracts, metric semantics, export diagnostics, and regression coverage explicit enough for external contributors to trust.

Public-repo quality focus:
- keep touched-file ownership, adjacent-doc sync, and acceptance evidence explicit
- preserve contributor readability, diagnostics, and static-analysis health alongside user-visible behavior
- prefer additive hardening over broad cleanup-only refactors that widen blast radius
- update tests, fixtures, screenshots, workbooks, or artifacts in the same change when behavior shifts
