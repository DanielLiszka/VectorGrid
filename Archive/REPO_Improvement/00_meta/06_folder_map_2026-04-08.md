# Folder Map Plan

Last updated: 2026-04-09

## Purpose

Define the responsibilities of each `REPO_Improvement` folder so new docs are filed consistently and future waves route quickly to the right part of the document tree.

## Scope Boundaries

In scope:

- top-level `REPO_Improvement` folder responsibilities
- routing between meta, shell, data, optimization, results, validation, artifacts, strategies, ML, live, tests/perf, and docs/ops folders
- how folder ownership should be interpreted during future waves

Out of scope:

- the application source tree itself
- options-related planning
- fine-grained per-file ownership beyond folder scope

## Current User-Facing Behavior

The folder structure already exists and is meaningful:

- `00_meta/`
- `01_shell/`
- `02_data/`
- `03_opt/`
- `04_results/`
- `05_validation/`
- `06_artifacts/`
- `07_strats/`
- `08_ml/`
- `09_live/`
- `10_tests_perf/`
- `11_docs_ops/`

The meta plan and README already treat this as the canonical short-path structure, but there is not yet a dedicated folder-map doc that states what belongs where.

- manual review of file placement
- folder-count summaries in the tracker

## Strengths Already Present

- the short-path folder scheme is already in place
- current docs largely respect the intended topical split
- folder counts already give a coarse coverage view

## Weaknesses / Failure Modes

- there is no single place that explains borderline cases
- some topics could plausibly fit multiple folders if routing rules stay implicit
- created-doc placement can drift if future waves prioritize speed over consistency

## Regressions To Avoid

- placing docs in folders based on convenience rather than ownership
- splitting closely related topics across folders without a reason
- letting `11_docs_ops` absorb unrelated product docs
- creating new top-level folders without updating the meta plan
- allowing this surface to stay behaviorally “working” while contributor readability, diagnostics, accessibility where relevant, static-analysis cleanliness, or regression coverage degrades in a public-facing repo

## Proposed Improvement Approach

1. Define one responsibility statement per folder.
2. Add routing notes for common boundary cases.
3. Keep the folder map aligned with the current short-path constraint.
4. Use the folder map when deriving future queues from the meta catalog.
5. Treat planning-layer quality as part of the implementation scope: keep the program auditable, explicit, refreshable, and easy for future contributors to execute without guesswork.

Public-repo quality focus:
- keep touched-file ownership, adjacent-doc sync, and acceptance evidence explicit
- preserve contributor readability, diagnostics, and static-analysis health alongside user-visible behavior
- prefer additive hardening over broad cleanup-only refactors that widen blast radius
- update tests, fixtures, screenshots, workbooks, or artifacts in the same change when behavior shifts

## Folder Responsibilities

- `00_meta/`
  - program-governance, tracking, execution, and cross-cutting planning rules
- `01_shell/`
  - application shell, workspace layout, settings, readiness, overlays, and general UX behavior
- `02_data/`
  - dataset discovery, loading, provenance, repair, cache state, and data-source workflows
- `03_opt/`
  - optimization request shaping, backend routing, strategy parameter surfaces, and optimization execution contracts
- `04_results/`
  - optimization-results presentation, analysis surfaces, charts, and decision-readability concerns
- `05_validation/`
  - validation workflows, verdict/stat semantics, workbook export behavior, and validation-state UX
- `06_artifacts/`
  - saved run artifacts, history library behavior, report persistence, replay, and artifact identity
- `07_strats/`
  - strategy-specific execution or presentation behavior outside the more generic optimization/validation shells
- `08_ml/`
  - ML Signal, meta-analysis, campaign orchestration, and ML-specific backend/frontend flows
- `09_live/`
  - live execution, broker/settings surfaces, runtime guardrails, streaming, and system-boundary concerns
- `10_tests_perf/`
  - automated verification, harnesses, parity tooling, perf/profile tooling, and quality gates
- `11_docs_ops/`
  - public-repo docs, release/build operations, governance docs, and repo-surface quality policies

## Boundary Rules

- if a document is about how a feature appears in the shell, it belongs in `01_shell/` even if a store is involved
- if a document is about request construction or backend route selection for optimization, `03_opt/` wins over `01_shell/`
- if a document is about how optimized or validated outputs are displayed, `04_results/` or `05_validation/` wins over `06_artifacts/`
- if a document is about save/load/replay/history behavior, `06_artifacts/` wins over the originating product area
- if a document is about test strategy, harnesses, perf gates, or parity scripts, `10_tests_perf/` wins even when the tests target another surface
- if a document is about repo-wide policy, public-facing quality, release behavior, or scope governance, `11_docs_ops/` wins
- do not create new top-level folders to avoid a boundary decision; resolve the boundary here and keep the short-path scheme stable

## Verification Plan

- spot-check new docs against the folder map before marking waves complete
- verify folder counts still align with the intended coverage split
- update the folder map if the meta plan adds or removes a top-level folder
- run the relevant repo quality gates for any touched surfaces, including `cargo check --workspace` or a justified narrower Rust target plus `npm --prefix web run lint` and `npm --prefix web run typecheck` where frontend or desktop code is touched
- verify the definition of done, refresh triggers, and any superseded/historical pointers are explicit enough that another contributor could continue the program without guesswork
- capture the concrete acceptance evidence for closure, such as updated test output, screenshots, saved artifacts, report workbooks, or benchmark/profile artifacts as appropriate

## Rollout / Fallback / Compatibility Notes

- apply this map without moving already-correct docs
- if an existing doc is clearly misplaced later, move it deliberately and update tracker paths in the same change
- keep the folder map descriptive and stable rather than overfitting one wave
- keep changes additive, preserve existing functionality, and avoid broad cleanup-only refactors unless they provide objective user or maintainer value and include the necessary migration notes
