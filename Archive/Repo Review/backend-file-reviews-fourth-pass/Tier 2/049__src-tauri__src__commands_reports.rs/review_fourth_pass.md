## Why This File Got A Fourth Pass

The third-pass packet was directionally right to keep this file in a small-bucket, compatibility-sensitive lane, but it still framed the file too much as a workbook-format surface and not enough as an artifact-persistence coordinator. That distinction matters now because the live file delegates the active XLSX layout work to `commands_reports_validation_xlsx.rs` and `commands_reports_csv.rs`, while its highest-risk local behavior is artifact reconstruction and save-back in `save_report_xlsx_from_artifact_blocking` (`commands_reports.rs:219-250`). This pass therefore re-checked the live source against the packet to see whether the biggest remaining risks were really format-shape risks or whether the packet was still underweighting persistence-side effects, wrapper drift, and contract boundaries.

The current third-pass bucket should stand. Nothing here justifies a broad redesign in the active product path. But the reasons for keeping the bucket small are sharper than the third pass stated: the safe-now work is mostly about narrowing contract looseness and eliminating a thin wrapper inconsistency, not about reworking workbook structure.

That broader behavior materially changes how `save_report_xlsx_from_artifact_blocking` should be assessed.

Together, that supports a conservative review posture: tighten real contract weaknesses first, and keep workbook-memory or transport churn deferred until measured need exists.

## What Fourth Pass Sharpened

The current third-pass bucket should remain `Small surgical refactor`. The file is still not a good candidate for broad structural work in the live product path, and the third-pass packet was right to resist cosmetic cleanup. It was also right that artifact-backed export ordering matters and that this module should be treated as compatibility-sensitive, because the command surface remains registered in Tauri and the headless helper remains re-exported from `commands.rs`.

What the third-pass packet got most right is the high-level restraint. The live validation XLSX path is already delegated to `commands_reports_validation_xlsx.rs`, the current reporting posture is validation-first, and the older analysis-style builders are clearly legacy/reference in the live source and repo map. That means broad workbook rewrites, naming churn, or memory-mode experimentation would still be the wrong move for this file now.

What it still underweighted is that the highest-risk local behavior is not workbook layout. It is artifact persistence. `save_report_xlsx_from_artifact_blocking` does not just reconstruct a report and store `report_xlsx_path`; it re-enters `save_run_artifact_blocking` after the workbook has already been written. In the live `run_artifacts.rs` implementation, that save path can enrich `env`, backfill `config_fingerprint_version`, normalize or augment `dataset_meta`, derive `route_provenance` and `lineage`, regenerate `optimization_metric_surface`, rewrite the full artifact JSON, and then run retention pruning for old untagged run artifacts. That is a materially broader side-effect surface than the third-pass packet described, and it is the clearest reason this file is artifact-contract-sensitive rather than merely format-sensitive.

That broader save-back path also exposes a narrower but more important edge case the packet missed: export from an older artifact is not necessarily idempotent. `build_validation_report_from_artifact` snapshots the current artifact into a report first, then `save_run_artifact_blocking` may enrich the artifact afterward. In practice, that means an older artifact missing `optimization_metric_surface` or other backfilled metadata can produce one workbook on first export and a slightly richer one on later export, because the save-back happens after workbook generation. That is not necessarily a product bug, but it is a real persistence/compatibility characteristic and a better reason to keep redesign deferred than the third-pass discussion of sheet names and placeholder cells.

The other live issue the packet missed is wrapper drift around `max_rows`. `build_report_xlsx_blocking` and `save_report_xlsx_for_base` both normalize `Some(0)` to `None` by filtering out non-positive row caps at `commands_reports.rs:56` and `commands_reports.rs:88`. `build_report_xlsx_bytes_headless`, however, forwards `Option<usize>` unchanged at `commands_reports.rs:66-70` even though its doc comment says it “mirrors `save_report_xlsx` generation behavior.” That is either a real semantics mismatch or, at minimum, a misleading contract description on a helper that is publicly re-exported for headless use. The prior packet correctly wanted a `max_rows = None` versus `0` test, but the fourth-pass read is stronger: this is not just missing coverage; it is an actual wrapper-consistency question in the live code.

The current packet also overstates one part of the risk surface. Treating header order, sheet names, placeholder text, and link targets as the primary live concerns is too broad for `commands_reports.rs` itself. Those concerns matter to the overall export product, but the active workbook layout and CSV shaping now live mainly in `commands_reports_validation_xlsx.rs` and `commands_reports_csv.rs`, which the repo map explicitly routes contributors to first. In this file, the most valuable review attention belongs on artifact reconstruction, save-back side effects, and wrapper/API consistency.

One earlier recommendation is also weaker than it sounded: direct test coverage for the `"artifact payload is not an object"` warning branch. On the current code path, `build_validation_report_from_artifact` runs before that branch and already requires `/validation/res` to exist. Under `serde_json::Value::pointer`, a non-object root cannot satisfy `/validation/res`, so that warning branch appears effectively defensive rather than realistically reachable on the accepted input contract. Keeping the branch is harmless, but prioritizing dedicated test work for it is not the best use of this bucket.

The older doc-hardening recommendation also needs to be deprioritized slightly versus the first-pass packet. The live source already includes targeted explanatory comments above `build_report_xlsx_bytes_headless` and above the legacy builder section stating that the active path is the validation workbook builder and the old builders are legacy/reference. A full module-level header could still help, but the source is not as under-documented on this point as the earlier packet implied. On the current evidence, persistence-side effects and wrapper drift are more urgent than additional top-of-file commentary.

## Implementation Priority

The safe-now hardening work should stay narrow. First, artifact-backed export should validate run-artifact kind before proceeding, and it should accept both currently supported run kinds (`vectorbt_run_artifact` and `vectorgrid_run_artifact`) rather than only the newer one. That recommendation still stands, and the supporting evidence is stronger than the third-pass packet made explicit because neighboring hydration code already performs that check. The main regression risk is that this would intentionally stop exporting arbitrary JSON files under `runs/` that merely happen to contain `/validation/res`. If that loose behavior is currently relied on anywhere, the contract should be named and kept intentionally; otherwise, tightening to canonical run artifacts is the safer backend stance.

Second, this file should add a targeted regression lock around the `max_rows` contract before any behavior change is made. The safest immediate step is a test proving whether `build_report_xlsx_bytes_headless(..., Some(0))` is intended to behave like the Tauri/save wrappers or not. If the intended product contract is “0 means unlimited/default,” then normalizing `Some(0)` inside the headless helper to match the wrappers is a justified safe-now change. If not, the doc comment on the headless helper should stop claiming it mirrors `save_report_xlsx` generation behavior. Either way, this is small, local, and less regression-prone than any workbook-structure work.

Third, if a portable test harness can support it, add direct backend coverage for `save_report_xlsx_from_artifact_blocking` on the realistic negative path: unsupported artifact kind. The prior packet’s broader call for warning-branch coverage should be narrowed. The non-object branch looks effectively unreachable on the accepted contract, and forcing cross-platform filesystem failures just to exercise the save-back warning may create brittle tests. A positive artifact-export smoke plus an unsupported-kind test gives better value for this bucket.

The larger redesign should still be deferred. The biggest deferred redesign is not legacy builder extraction; it is disentangling report-path persistence from full run-artifact save semantics. If the product eventually wants report export to be a narrow metadata update rather than a full artifact rewrite, the right structural move is a dedicated “update `report_xlsx_path` in an existing run artifact” helper in `run_artifacts.rs` instead of reusing `save_run_artifact_blocking`. But that is a behavior decision, not a casual cleanup: the current broader save-back path may be intentionally providing late artifact enrichment, and replacing it would change when dataset metadata, route provenance, lineage, and optimization metric surface get materialized. It would also change whether export can trigger ordinary run-artifact pruning. That is real persisted-behavior churn and should remain deferred unless the team explicitly wants that contract change.

Legacy builder isolation remains a valid deferred cleanup, but it is still second-order here. The file is large, and moving `build_report_xlsx_analysis_v2` plus the older builder into a clearly named legacy module would improve maintainability. Still, the live source now already labels those builders as legacy/reference, and removing or relocating them has a wider review blast radius than the tighter artifact-side fixes above. Naming churn on the public command surface and workbook memory-mode changes remain deferred for the same reasons given earlier: they touch compatibility and performance semantics without evidence of a clear bug in the active path.

## Regression And Feature-Preservation Constraints

Preserve the current validation-first export path. The active workbook builder remains `commands_reports_validation_xlsx::build_validation_report_xlsx`, and this file should continue to delegate there unless the adjacent validation-report modules are being changed together.

Preserve current artifact-to-report passthrough behavior unless downstream consumers move together. `build_validation_report_from_artifact` is more projection than normalization, and the earlier packet was right to treat it as compatibility-sensitive even where Rust typing would allow cleanup. In particular, do not casually drop or reshape `run.*`, `validation.*`, or `optimization_metric_surface` passthrough fields under the banner of cleanup.

Do not silently change `max_rows` semantics for headless callers without first locking in the intended behavior. The headless helper is a re-exported backend surface, not a private local convenience. Even a one-line normalization fix should be treated as a compatibility adjustment rather than an invisible cleanup.

Be explicit about the behavioral cost of any save-back narrowing. Replacing `save_run_artifact_blocking` with a narrower report-path patch helper would reduce surprising side effects, but it would also stop any incidental enrichment and could change retention/pruning behavior. That is a valid redesign only if the team prefers report export to be a strictly narrower persistence action.

Keep public command names stable in this bucket. Whatever the live naming imprecision around generic “report” wording, the Tauri command surface remains registered and consumed downstream. A naming cleanup is not justified here unless multiple layers move together intentionally.

## Fourth-Pass Conclusion

The current third-pass bucket should stand. `src-tauri/src/commands_reports.rs` still belongs in `Small surgical refactor`, and the third-pass packet was right to avoid broad workbook or API churn. What the third pass got right was the restraint: the active validation-report path is already delegated, the command surface is real, and compatibility matters more than style cleanup.

What the third pass still missed or underweighted is where the live risk actually sits now. In this file, the sharpest issue is not workbook formatting. It is that artifact-backed export currently reuses full run-artifact save semantics, which broadens the mutation surface beyond `report_xlsx_path`, can make first export from an older artifact non-idempotent, and can trigger ordinary run-artifact pruning. The packet also missed a thinner but real wrapper inconsistency: the headless helper claims to mirror save behavior while not normalizing `max_rows` the same way as the public/save wrappers.

The safe-now recommendation therefore narrows to three items: validate run-artifact kind before artifact-backed export proceeds, add direct regression coverage around artifact-backed export on the realistic negative path, and lock down the `max_rows` contract before changing or documenting the headless helper. The larger redesign should remain deferred: if the team wants report export to stop piggybacking on full run-artifact save semantics, that should be an intentional persistence-contract decision, not a small cleanup slipped into this file.
